  - [x] **Real-hardware print bugs found + fixed (2026-09-13)** — first print to an actual "POS-80" thermal printer surfaced two separate defects:
    - **Blank tail below the receipt.** `@page { size: 80mm auto; margin: 0 }` is not valid CSS — the `size` descriptor accepts one or two `<length>` values, the bare keyword `auto`, or a named page-size, never a length *and* `auto` together — so Chrome silently drops the whole declaration and falls back to whatever fixed paper size the printer driver advertises (here, its own "80 x 210mm" preset), leaving a large blank tail below a short receipt. Fixed in `thermal-receipt.svelte` by measuring the rendered `.tr-page`'s actual height client-side (`getBoundingClientRect`, px→mm at 25.4/96) via a `ResizeObserver` (re-measured on mount, on size change, and on `beforeprint`) and declaring a real, exact `@page` height from it instead of `auto`. **Confirmed still not fully resolved on this hardware** — the "POS-80" driver's Chrome print dialog only ever offers the one fixed "80 x 210mm" preset with no custom/continuous-length option, so Chrome can't honor a smaller requested height regardless of what `@page` asks for; that ceiling is the Windows driver's own paper-size list, outside what a web page's CSS can override. Left as a known hardware limitation, not further "fixed" in code — the content itself is otherwise correct and the wasted paper is cosmetic, not a data/legibility problem.
    - **Faint print — only bold/black text was legible.** The thermal component used a two-tone ink system copied from the A4 world (`--tr-ink: #000` primary, `--tr-muted: #444` for labels/secondary lines) at the browser's default (400) font-weight for anything not explicitly bolded. A 203dpi thermal head reproduces true gray and thin strokes very poorly — normal-weight `#444` printed too faint to read, matching exactly what the user reported. Fixed by dropping the gray entirely (`--tr-muted` now equals `--tr-ink`, solid `#000` everywhere — hierarchy in this monochrome format comes from weight/size/rules, not shade, same as a real receipt), raising the page's base font-weight from the implicit 400 to 500, and bolding row values specifically (`.tr-row span:last-child`, 600) so a label/value pair still reads with some contrast now that color no longer carries it.
    - **Solid-black doctype block was expensive to print.** `.tr-doctype-block` (the "OFFICIAL RECEIPT / No. OR-000007" header) was an inverted white-on-black fill — on a thermal head that means burning the *entire* block edge to edge, which draws far more heat/energy and wears the print head faster than outlined text of the same size (flagged directly by the user after a print, "it will cost too much on the printer"). Replaced with a bordered box (thick top/bottom rule, thin sides, black ink on white) that reads as the same "this is the important part" emphasis without ever laying down a solid fill; `.tr-copy-tag`'s border flipped from white-on-black to black-on-white to match. `pnpm check` green; not yet re-verified on the physical printer.

  - [x] **Multi-room walk-in search rejected valid party-size/room-count combos (2026-09-13)** — reported live with a screenshot: 3 guests + 2 rooms against a max-occupancy-2 room type returned "No rooms available for these dates/occupancy," even though 2 rooms × 2 guests each is genuinely enough capacity for 3. Root cause: `searchAvailability`'s room-type filter checked `roomType.maxOccupancy >= occupancy` — the capacity of *one* room against the party's *total* guest count — with no `roomCount` factor at all, so any party bigger than a single room's max was rejected outright regardless of how many rooms they were asking for. Fixed by filtering room types against `maxOccupancy * roomCount >= occupancy` instead (moved from a SQL `gte` clause to a JS filter over the fetched room types, since `roomCount` is a request parameter, not a column). `booking-modify.ts`'s equivalent occupancy check already did this correctly (`effectiveMaxOccupancy * bookingRoom.quantity`) — only the search/browse path had the bug. This was very likely the actual root cause behind "I can't select two rooms" reported the same session: any realistic multi-room party size (more guests than one room alone could hold) silently made every room type disappear from the results before staff ever got to a room-count choice. `pnpm check`/`test` green; live-DB reproduced against `hotel1`'s real "Deluxe twin" (max occupancy 2) with the exact reported inputs (occupancy 3, roomCount 2) — now correctly returns it with 2 rooms available.
