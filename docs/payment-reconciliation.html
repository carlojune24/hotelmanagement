Payment Verification & Reconciliation

mmhotel · PayMongo payments that confirm themselves, with a tamper-evident money trail. Live Deployed 15 Oct 2026 · main 5e3bd41 · migrations 0101–0102

The problem it fixes

A booking used to be confirmed only when PayMongo's webhook reached our server. When it could not (a dead ngrok tunnel in dev, an outage, a missing event subscription) the guest sat on "Waiting for confirmation… (check 1 of 12)", gave up after about 36 seconds, and a refresh lost the state. Real money could sit in PayMongo while the booking stayed pending_payment, and the 60-minute hold sweep could then cancel a paid booking and release the room.

How it works now

Guest pays on PayMongo→ Webhook lost?→ We ask PayMongo directly→ Payment recorded & booking confirmed→ Entry on the money trail

Every checkout session we create is stored forever in payment_attempts. A checkout is paid when PayMongo's session payments[] holds a payment whose own status is paid (the session's own status stays active). The same confirm code runs from every path, so a webhook and a verifier arriving together record one payment (unique index on the paid pay_ ID).

What asks PayMongoWhen
Guest's confirmation pageOn every load / refresh while pending (throttled, one look per order every ~4 s) and the "Check again now" button
Background worker payment_verify (pg-boss)Every minute. Backoff per attempt: every minute for ~10 min, every 5 min up to 1 h, then every 15 min, for as long as the session can still be paid. No retry cap.
Webhook payment.paidNudges an immediate check of the hotel's open attempts
Hold sweep (room and dining)Asks PayMongo first. A paid booking is confirmed, never cancelled. If PayMongo cannot be asked, orders under 24 h old are not cancelled.
Safety net paymongo_syncEvery 15 min, mirrors PayMongo's own records for the Finance → PayMongo tab

What guests see

While waiting

  • Never "gave up": polling has no cap (3 s → 5 s → 10 s → 30 s)
  • Booking code and a PC-XXXXXXXX payment check code
  • "Check again now" button; a refresh recovers instantly
  • "Pay" reuses an open checkout instead of creating duplicates

Once paid

  • Payment reference pay_… (copy button) and pi_…
  • Same reference in the confirmation email
  • Dining orders get the same treatment

Emails (best effort, once each)

  • Track your payment: sent when they start paying, with the link
  • Still checking: sent once if unconfirmed after ~10 min ("do not pay again")
  • Confirmation: now includes the pay_… reference

The tracking link is the existing /{slug}/confirmation/{orderId}?t={token} (room) or /{slug}/dining/order/{code}?t= (dining): unguessable, no login, works on any device.

What staff see

  • Booking page (management/transactions/[orderId]): "Online payment attempts" list with amount, status, pay_/pi_/cs_ IDs, check code, times checked, last error.
  • Find by number accepts pay_…, pi_…, cs_… and PC-… codes.
  • Finance → Reconciliation (new tab, needs finance:read), below.

Finance → Reconciliation tab

Integrity banner

Re-checks the whole money trail on every visit: green "Money trail verified" with the latest fingerprint, or a red warning naming the broken entry.

Needs attention

  • Cannot verify: PayMongo could not be asked yet (auto-retries)
  • Paid, not recorded: PayMongo has it, our write failed (auto-retries)
  • Refund due: paid after the booking was cancelled
  • Not on the trail: recorded but its trail write failed

Settled automatically

One row per payment the verifier recovered. "Details" shows the timeline: checkout started → PayMongo took it → missing from our books (for how long) → found and recorded, with how it was found, amounts asked vs received, status before/after, every ID, check code, and the trail fingerprint. Filter by date and type; Print; CSV.

Security of the money trail

  • Append-only table payment_reconciliation_events: database triggers refuse UPDATE, DELETE and TRUNCATE.
  • Hash chain: each row stores SHA-256 of its content plus the previous row's hash (per hotel, per seq). Any edit made around the triggers breaks every hash after it; the tab shows it.
  • Serialised writes: a per-hotel advisory lock stops parallel writes from forking the chain (tested with 12 parallel appends).
  • No personal data and no foreign keys in the trail; names are read from the booking when displayed.
  • Exports are audited (reconciliation.exported in the Audit log, with who and when); guest names are neutralised against spreadsheet formula injection; pages and CSV are served no-store.
  • A failed trail write never blocks a real payment: it is logged, and the payment shows as "Not on the trail" for follow-up.
Limit: a database admin could still drop the triggers; the chain would expose any edit, but only if someone checks. For proof that nothing changed later, note the latest fingerprint from the banner (for example at month-end).

Operations

Check it is healthy (production)

  • pm2 logs mm-hotel shows [jobs] payment_verify: { … errors: 0 } every minute.
  • Reconciliation tab banner is green and "Needs attention" is 0.
  • Server DB: select status, count(*) from payment_attempts group by 1;

Deploy

Commit to Jade, merge into main in a clean worktree of origin/main, then from that worktree run bash scripts/deploy.sh --migrate (--migrate whenever a migration is added). Server mmserver@100.109.167.10, pm2 app mm-hotel, port 3011, live hotel slug mmhoteltandag.

Testing locally without a tunnel

Run the dev server with no ngrok, book, pay on the PayMongo test page, return. The page confirms within seconds with the pay_… ID; the trail shows the entry as found by the guest page or the worker.

Known gaps

No Official Receipt series: the server logs "No active Official Receipt series is registered" on online payments. Payments still record and confirm, but no official receipt is issued until a series is added in Finance → BIR → Series.
  • Bookings paid before 15 Oct 2026 have no payment_attempts row and are not tracked by the verifier.
  • The live PayMongo webhook subscription has not been checked for payment.paid; it no longer matters for confirming payments.
  • Dining rows on the Reconciliation tab link to the dining orders page, not to the individual order.
  • The trail records reconciliations and failures, not every ordinary webhook payment.
